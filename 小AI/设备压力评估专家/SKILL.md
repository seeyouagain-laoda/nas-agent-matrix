# 设备压力评估专家

给家庭 NAS（飞牛 fnOS 及其他 Linux NAS）上的常驻智能体服务做**部署前评估**和**运行中排障**。
核心主张：**先算账，再部署**。绝大多数「跑不动」「莫名其妙卡死」都源于部署前没算过这笔账。

---

## 一、四类压力评估铁律

### 1. CPU 压力

| 指标 | 安全线 | 告警线 | 危险线 |
|---|---|---|---|
| 平均负载（15min）/ 核心数 | < 0.7 | 0.7 ~ 1.0 | > 1.0 持续 |
| 单核软中断占比（si%） | < 5% | 5% ~ 15% | > 15% |

**铁律**

- **看 15 分钟平均负载，不看瞬时值**。智能体任务是突发型的，瞬时飙高正常，持续飙高才是问题。
- **负载要除以核心数**。「load = 8」在 4 核上是红灯，在 16 核上很闲。
- **预留至少 30% 余量给突发**。你评估出「刚好够用」= 实际上不够用。
- **向量检索 / 嵌入计算是 CPU 大户**。开了 RAG 或本地 embedding 的服务，CPU 占用通常是纯 LLM 转发的 3~5 倍，评估时要单列。

```bash
# 看负载与核心数
uptime && nproc
# 实时看每核占用，1 = 单核打满
top -1
# 看软中断是否异常（网络包处理瓶颈的信号）
vmstat 1 5
```

### 2. 内存压力

| 指标 | 安全线 | 告警线 | 危险线 |
|---|---|---|---|
| 可用内存占比 | > 30% | 15% ~ 30% | < 15% |
| swap 使用量 | ≈ 0 | 缓慢增长 | 持续增长且 si/so > 0 |
| 容器 OOM 次数 | 0 | — | ≥ 1 |

**铁律**

- **「free 里 buff/cache 被占满」不是内存不足**。Linux 会用空闲内存做缓存，要看 `available` 那一列。
- **swap 开始被使用 = 已经在告警**，不是「还有 swap 兜底所以没事」。
- **给每个容器设内存上限**。不设上限的容器 OOM 时会拖垮整机，甚至把 SSH 一起干掉。
- **预留 1~2 GB 给系统自身**。NAS 还有自己的系统服务、Docker daemon、文件索引在跑。

```bash
# 看真实可用内存
free -h
# 按内存占用排序看容器
docker stats --no-stream --format "table {{.Name}}\t{{.MemUsage}}\t{{.MemPerc}}"
# 查是否被 OOM kill 过
dmesg -T | grep -i "out of memory"
journalctl -k | grep -i oom
```

### 3. 磁盘压力

| 指标 | 安全线 | 告警线 | 危险线 |
|---|---|---|---|
| 根分区使用率 | < 70% | 70% ~ 85% | > 85% |
| 日志目录增长速率 | 稳定或有轮转 | 持续增长 | 无轮转且快速增长 |
| inode 使用率 | < 70% | 70% ~ 90% | > 90% |

**铁律**

- **85% 是硬红线**。很多文件系统到 85% 后写入性能断崖式下跌，还有的会直接拒绝写入导致服务崩。
- **先查日志，再查数据**。智能体服务跑几个月后，九成磁盘爆满都是日志没配轮转。
- **inode 也会耗尽**。大量小文件（缓存、分片、碎片日志）会把 inode 吃光，表现为「还有空间但写不进去」。
- **数据库文件要单独评估**。向量库 / sqlite 会持续增长，必须给它们单独的上限策略或定期清理。

```bash
df -h && df -i
# 找出最占空间的目录（先看日志再看数据）
du -xh --max-depth=2 / 2>/dev/null | sort -rh | head -20
# Docker 占用总览
docker system df
```

### 4. 带宽压力

| 指标 | 说明 |
|---|---|
| 上行带宽 | 家庭宽带通常上行只有下行的 1/10，**先看上行** |
| 单节点带宽 | 反代 / 代理节点的实际吞吐，不是标称值 |
| 并发连接数 | 长连接（WebSocket）会持续占用，不是按请求算 |

**铁律**

- **家庭宽带的瓶颈永远是上行**。评估外网访问能力时只算上行，忽略下行。
- **长连接按「并发数 × 单连接速率」算，不按峰值算**。WebSocket 长连接的占用是持续的。
- **内网访问和外网访问分开评估**。走 Tailscale 等组网方案的流量路径和直连完全不同。
- **给带宽留 50% 余量**。智能体的流量是突发型的，评估值当峰值用的话日常会卡。

```bash
# 看实时带宽占用（按进程）
nload
iftop -i eth0
# 看监听端口与连接
ss -tulnp
ss -s
```

## 二、部署决策流程

```
1. 摸家底：nproc / free -h / df -h / 上行带宽实测
      ↓
2. 算需求：把要跑的服务逐项列出，各自估 CPU/内存/磁盘/带宽
      ↓
3. 对红线：任一指标进入「告警线」→ 砍服务或加配置
      ↓
4. 选部署形态：单端 or 双端（见第三节）
      ↓
5. 上约束：给每个容器设内存上限、给日志配轮转
      ↓
6. 跑基线：空载跑 24h，记录四项基线值
      ↓
7. 常态化：按基线设告警阈值
```

**关键：第 6 步不能跳过。** 没有基线，后面的告警阈值全是拍脑袋，要么天天误报，要么真出事时不响。

## 三、双端部署（Windows + NAS）

### 什么时候需要双端

| 场景 | 建议 |
|---|---|
| 只有 NAS，任务都是无头命令 / 文件操作 | **单端（NAS）即可** |
| 需要操作 GUI 软件、浏览器自动化、需要本机文件 | **必须双端**，GUI 端放 Windows |
| 需要 7×24 常驻 + 临时重活 | **双端**，常驻放 NAS，重活放 Windows |
| NAS 配置较弱（≤ 4 核 / ≤ 8G） | **双端**，把重负载卸载到 Windows |

### 双端分工原则

```
NAS 端（常驻、低功耗、7×24）
  - 消息网关 / Bot 接入（QQ、微信等）
  - 定时任务与日程触发
  - 轻量命令执行、文件读写
  - 记忆库、数据库等状态服务

Windows 端（按需唤醒、高算力、有 GUI）
  - 浏览器自动化（CDP）
  - GUI 软件操作
  - 大模型本地推理 / 重计算任务
  - 显卡相关负载
```

**铁律**

- **状态服务只放一端**。记忆库、数据库这类有状态服务双端各起一份 = 数据分裂，是灾难不是冗余。
- **两端都要有健康检查**。双端意味着故障面翻倍，任何一端静默挂掉都会让任务无响应且不报错。
- **明确任务路由规则**。写清楚「什么任务走哪端」，含糊的规则会导致任务在两端反复横跳。
- **网络要能互通**。优先走组网方案（Tailscale 等），不要暴露端口到公网。

### 双端压力叠加计算

双端部署时，**NAS 端的评估不能只算自己那份**：

```
NAS 端总负载 = NAS 自身服务 + 转发给 Windows 端的代理开销 + 两端心跳/同步开销
```

代理转发和心跳同步看着不大，但它是**持续占用**，要在基线里单列出来。

## 四、常见故障速查

| 现象 | 优先怀疑 | 检查顺序 |
|---|---|---|
| 命令超时、无响应 | CPU 打满 或 内存 OOM | `uptime` → `top -1` → `dmesg \| grep oom` |
| 服务写入失败但磁盘有空间 | inode 耗尽 或 分区 quota | `df -i` → `quota -s` |
| 隔一段时间就卡一次 | 日志轮转 / 定时任务 / 内存泄漏 | `crontab -l` → 对比基线内存曲线 |
| 外网访问慢，内网正常 | 上行带宽打满 | `nload` → 检查是否有大流量任务在跑 |
| 容器反复重启 | 内存超限被 kill | `docker inspect <容器> \| grep -i oomkilled` |
| 整机 SSH 都连不上 | 某容器没设内存上限，拖垮整机 | 物理重启 → `docker stats` 找元凶 → 补上限 |

## 五、输出规范

给出评估结论时，必须包含：

1. **四项指标的当前值与判定**（安全 / 告警 / 危险）
2. **明确结论**：能不能部署、需要砍什么或加什么
3. **具体的约束配置**：内存上限、日志轮转、磁盘清理策略
4. **基线记录建议**：空载 24h 后记录哪些数值

不确定时，**按更保守的估计给结论**，并说明保守在哪里。宁可让人少跑一个服务，也不要让人整机崩掉。

---

## 六、绝对禁止

- **不设内存上限就跑容器**。
- **日志不配轮转就上线**。
- **在磁盘 > 85% 的设备上继续加服务**。
- **把有状态服务双端各起一份**。
- **只看「命令返回 0」就判定部署成功**——要跑真实负载验证。
